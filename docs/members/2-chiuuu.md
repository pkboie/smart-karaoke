## 跨裝置延遲初測（2026-11-28）

測試方式：在 Smart Karaoke 網頁使用「延遲校正（喇叭測試）」，以喇叭播放 Beep、由麥克風收音；每組 5 次，記錄原始數值、系統估計值及是否通過穩定性檢查。這是**聲學回錄延遲粗估**，不是已驗證的單向麥克風延遲或演唱補償值。各設備的型號、音效裝置與環境尚未完整記錄，因此先作為跨裝置初測。

| 裝置 | 三組系統顯示的估計值／中位數（ms） | 量測狀態與觀察 |
| --- | --- | --- |
| 自己的筆電 | 曾得到 24.7、62.0、10.0、19.3、190.0 等差異很大的數字 | 多次波動大，有近零值與明顯離群值；僅少數通過程式穩定性判斷 |
| A 同學 | 8.7、8.7、8.7（**均未通過**） | 初次戴耳機導致麥克風無法收到喇叭回錄；改用喇叭後仍有大量 0.7 ms 可疑值，15 筆原始值中 10 筆為 0.7 ms |
| B 同學 | 88.7、99.3、99.3 | 三組均通過程式穩定性檢查；三組中位數的中位數為 **99.3 ms** |
| C 同學 | 99.3、99.3、91.3 | 三組均通過程式穩定性檢查；三組中位數的中位數為 **99.3 ms** |

### 初步觀察與限制

- **B、C 有較好的重複性**，但數值接近只代表量測程序輸出一致，不能證明 99.3 ms 就是正確的演唱補償值。
- **A 與自己的筆電較不穩定**。A 出現大量 0.7 ms，推測與 RMS 門檻誤觸發、音效裝置或瀏覽器排程等因素有關，尚無證據能歸因於電腦較舊。
- **耳機與喇叭要分開測**：戴耳機時內建麥克風通常無法收到耳機播放的 Beep；這不等於麥克風或網頁本身故障。
- 系統在量測不穩定時不自動套用補償，保留手動輸入；正式報告應揭露成功與失敗案例，不只挑選穩定結果。

## 卡住／需要別人

- **延遲校正的準確性仍待驗證**：RMS 門檻有誤判風險；穩定結果並非硬體延遲的 ground truth。
- **耳機延遲測量尚未完成**：需另外設計 loopback 或其他可驗證方法；目前僅有喇叭到麥克風的聲學回錄粗估。
- **音訊時間同步精度**：小星星的伴奏、白色音高線、評分與 trace 均正常，但尚未量化 AudioWorklet frame 與伴奏的對齊誤差。
- **與 #1／#4／#6 協調**：後續更新 `main.js`、`processAudioFrame()` 時留意時間基準與分支衝突；E2 的 pitchy 需在瀏覽器內量測，不直接拿 Node 啟動總耗時比較。

## 筆記與限制

- `latency-calibration.js` 現在主要使用麥克風 RMS 偵測 Beep；**量到的是粗略的喇叭到麥克風聲學回錄延遲**，包含音訊裝置、聲音傳播及偵測誤差，並非已驗證的單向演唱補償值。
- 小星星端到端功能通過，只代表播放、收音、評分流程可執行；**尚未量化收音和伴奏的同步誤差**。
- E2 的初步記憶體量測包含 Python 主程序／子程序 RSS，並有 profiler 開銷；pitchy 另有 Node.js 啟動與取樣差異，正式報告需清楚界定比較範圍。
- `data/` 下的錄音、trace 等測試資料不會跟著 Git 提交；提交前避免直接使用 `git add .`。
